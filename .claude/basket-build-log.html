How it fits together

A shopper uses the Angular app; everything else happens behind the Spring Boot service. Two local AI pieces do the heavy lifting: a small embedding model turns search text into vectors, and a 14-billion-parameter model picks each shopper's final five products.

  3. Aug 31from notes
    ML

    Every product gets a text embedding

    • 49,688 products embedded as 384-dimension vectors with bge-small, in 692 s on the laptop.
    • Gemini's free tier was tried first and dropped: it counts every product against quota, which put the job at 8–9 hours.
  4. Sep 1–3from notes
    ML

    Search design, and a collapsed model fixed

    • Search blends meaning-based and keyword results with Reciprocal Rank Fusion. No vector index, by choice: exact search takes 300–390 ms and never misses a match.
    • The August recommendation model had collapsed: its product vectors had an effective rank of 1.65 of 128, and picks were no better than chance.
    • Retrained on Sep 3 with temperature scaling and in-batch negatives: effective rank 6.26, and department matches 4.09× better than chance, up from 1.40×.
  5. Sep 4–5files + notes
    Pipeline

    The recommendation pipeline

    • A local Ollama model, qwen2.5:14b, picks the final five from about 100 candidates, discarding any product it invents. 27.7–43.5 s per shopper.
    • Candidates come from two sources: the shopper's last search, and products similar to what they usually buy.
    • Python precomputes shopper vectors and serves search-text embeddings; the Angular app gains a search page.
    • A background job prepares a follow-up text 15 minutes after a search. It logs the message instead of sending it.
  6. Sep 12–13this week
    SMS

    Real text messages

    • A Twilio sender was added and tested with real messages to a verified phone.
    • Plain test messages arrived. Both product-list messages were reported delivered but never reached the phone.
    • Cause: under India's DLT rules, carriers silently drop promotional-looking texts from unregistered senders, after reporting delivery. The code works; delivery needs DLT registration on the Twilio account.
  7. Sep 13this week
    Caching

    Redis caching

    • Each shopper's recommendations are cached for 30 minutes: 52.8 s → 0.23 s on a repeat read.
    • A new recommendations endpoint, and a Recommended for you section on the dashboard that shows how long each load took.
    • Search results are cached per query for 10 minutes and shared by every shopper: 11.1 s → 0.38 s.
    • Repeating the same search no longer throws away a shopper's recommendations.
  8. Sep 14this week
    Hardening

    Making it hold up

    • Recommendations are now computed in the background right after a search: the first dashboard load dropped from about 40 s to 0.62 s.
    • Found and fixed a race where searching bread, then milk, cached bread recommendations for the milk search.
    • Tested a smaller model, qwen2.5:3b. Four times faster, but its picks were mostly unrelated to the search, so it was rejected.
    • Moved Redis from the laptop to Upstash. Cache reads stayed as fast: 0.36 s.
    • The database pool now keeps idle connections alive, fixing errors that appeared after the laptop slept.
    • Only one recommendation run happens per shopper and search; a second request waits for it instead of starting another.

Decisions we stand by

Keep the 14B model
The 3B model is four times faster, but it recommended coffee and baby food to someone searching for milk. Background computation already removed the wait, so the speed buys nothing.
No vector index
At 49,688 products, exact search is 300–390 ms and never misses a match. Revisit only if traffic grows or the app moves next to the database.
“Delivered” isn't received
Indian carriers can drop a text after telling Twilio it was delivered. Confirm on a real phone before trusting the dashboard.
Caches fail quietly
If Redis is down or a password is wrong, the app keeps working, just slowly. Unexpected slowness is the symptom to investigate, starting with the logs.
Benchmark with varied inputs
Ollama reuses work from a repeated prompt, so the second identical request can look about seven times faster than a real one.

Still open

Fix soon

Risks to the project itself

  • Credentials are exposed. The Redis password was shared in a working session and hasn't been rotated, and the database password sits in plain text in the app's config file.
  • No version control. The project isn't in git, so none of these seventeen days can be reviewed or rolled back.
  • No automated tests. Caching, the background computation and the duplicate-run fix were all verified by hand; the only test is the default one from day one.
Watch

Works today, may bite

  • Memory is tight. The 14B model holds 9 GB of the laptop's 16, and the app was killed for low memory twice on Sep 14.
  • The sleep fix is unproven. The database keep-alive change can only be confirmed after the laptop next sleeps with the app running.
  • Restarts log everyone out. The app has been started with a fresh random session key each time.
  • Caching needs its settings. Starting the app without the Redis environment variables runs it with no caching at all.
Later

Product and model work

  • Texts to Indian numbers need DLT registration of the sender and message template.
  • A dashboard load right after a search still waits 50–60 s once, while the model finishes.
  • Duplicate-run protection only works within a single running copy of the app.
  • The product side of the model has no per-product embedding, and snacks and international foods were over-represented. From earlier notes, not re-checked.
  • The balance between search and taste in recommendations was measured with a stand-in for real searches and hasn't been re-measured. From earlier notes.
